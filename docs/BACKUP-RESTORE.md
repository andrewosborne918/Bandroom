# Backup and restore runbook

Backups are not active until an operator supplies the independent encrypted destination and schedules `scripts/backup-cloud.py`. Supabase Pro daily DB snapshots alone cannot restore audio. The streaming script exports public + Auth schemas, copies all private objects, and writes hashes/byte counts and a manifest last. A folder without manifest.json is incomplete. It does not export server secrets or custom SMTP configuration. Storage enumeration and DB export are not a single atomic snapshot; for a strict recovery checkpoint, disable mutations and stop workers during capture. Nightly online backups are best effort and may need reconciliation of concurrent changes.

Install Python backup dependencies and a matching PostgreSQL client, configure the environment variables in `.env.example`, and schedule the script nightly in a trusted job/container. Set S3 server-side encryption, deny public access, enable versioning, expire current and non-current backup versions after 30 days, and restrict deletion and restore permissions. Do not put backup credentials in Vercel public variables. Monitor `backup.completed`; alert if no completed manifest is present for 26 hours. A nightly backup implies up to approximately 24 hours of data loss, subject to successful capture. Actual recovery time is unmeasured.

Recovery procedure:

1. Disable AI and public writes, retain incident logs without customer content, and pick the last complete manifest. Restore to a new isolated project, never directly onto a live database as an initial test.
2. Download database.dump to a restricted directory and compare its SHA-256 and size to the manifest. Prefer Supabase's managed recovery for its Auth/storage internals. `pg_restore --list database.dump` permits inspecting the custom archive. Public data restoration must use a compatible migrated schema; provider-managed Auth restoration should be coordinated with Supabase support or its documented restore path. A generic `pg_restore --clean` against a managed project is not safe.
3. Restore each manifest object from encrypted backup S3 to its original private bucket/object key using the Supabase service credential in the trusted operator environment. Stream bytes, validate SHA-256 before declaring success. Do not restore expired ZIPs if unnecessary. Keep all buckets private and do not recreate public URLs.
4. Verify object references against audio_assets, release stale reservations and jobs, reconcile usage with the maintenance RPC, and verify no missing counted originals/stems. Start a fresh scoped worker with rotated secrets. Restore custom SMTP/domain/redirect settings from the environment configuration, not the database dump.
5. Verify two-band access isolation, authenticated downloads, invitations, actual audio decoding and audience exclusion. Perform staging playback on phones. Record duration, missing data and the operator's approval before redirecting production traffic. Keep the old project read-only until accepted.
6. Re-enable monitoring and scheduled backups. Retest quarterly and after changes to storage or authentication. Record completed drills in an operator incident log.

Local test evidence covers SQL migrations, RLS and cleanup accounting. No remote database/file backup or provider restore drill was performed in this session because credentials were unavailable.
